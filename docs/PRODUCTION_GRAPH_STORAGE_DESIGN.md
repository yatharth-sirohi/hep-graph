# Production graph storage: Phase 0/1 design

> V0.3 scope update: production uses manually built, validated, immutable snapshots. Automatic synchronization, incremental ingestion, scheduled reconciliation, and automatic promotion are deferred to v0.4+. The architecture below is a target, not a description of an already deployed system.

**Status:** discovery and local sample, 2026-09-16. No production cutover or cloud resource was created. The saved pilot is deliberately incomplete and must never be promoted as a complete graph.

## 1. Current bottleneck and implementation

The live path repeatedly pages INSPIRE author and literature searches, then rebuilds a guarded, deduplicated RAM snapshot. HLBES itself is transport independent and uses `UNKNOWN` / `PARTIAL` / `COMPLETE` neighborhoods. Its exact proof advances a completed radius only through `COMPLETE` expansions; a verified route is an upper bound, and timeout or incomplete retrieval cannot establish `NO_PATH`. Keep that mathematics (`hepgraph/hlbes.py`). `DeepSession` owns an in-memory SQLite evidence store, `Graph`, the identity guard, pagination and the `_LiveOracle` (`hepgraph/deep_search.py`). The legacy bounded on-demand path is separate (`hepgraph/ondemand.py`).

Existing live measurements are decisive: a Hostert small-team page of 40 works was 70,856 bytes with current fields; 25 Aad >10-author records were 10,352,493 bytes, about 414 KB each. A 1,515-record Aad large-team neighborhood would be roughly 600 MB with current fields. INSPIRE returned no compression for the tested requests. Five small-team author queries were reduced from about 19 pages to two by a bounded OR union, but the >10 mode remains payload bound (`docs/INSPIRE_NEIGHBORHOOD_API_AUDIT.md`). Local/Vercel requests also depend on open function invocations; jobs, cache, pacer and single-flight are process-local, so instance affinity is observed, not guaranteed (`docs/VERCEL_PERFORMANCE_HARDENING_REPORT.md`). Progressive first-route delivery is already implemented; a verified route can be shown while the proof continues (`docs/PROGRESSIVE_ROUTE_DELIVERY_REPORT.md`).

Mode semantics are `min_authors=1,max_authors=10` by default, `11..all` for large-team, and `1..all` for uncapped. `Graph` filters eligible article/conference records by the **true** `author_count`, excludes standalone leading Erratum/Errata/Corrigendum, applies earliest documented year with unknown years excluded from bounded-year searches, and counts distinct eligible shared works before `min_shared`. Genealogy is an independent doctoral overlay. The pipeline chooses one authoritative representative for duplicate DOI/arXiv groups without merging conflicting bylines. Search accepts numeric INSPIRE author IDs, ORCID and names, but names are search labels and never identity keys. The guard checks byline/profile forms, dates and known collisions, conservatively leaving compound surnames uncertain; normalized accents and documented aliases help lookup. Valid evidence retains INSPIRE record links and source IDs. These rules need parity tests before a new provider serves routes (`hepgraph/graph.py`, `hepgraph/pipeline.py`, `hepgraph/identity_guard.py`, `docs/IDENTITY_COLLISIONS.md`).

The saved snapshot loader has hard limits of 50,000 people, 100,000 works and 1,000,000 eligible occurrences; these are unsuitable for a full production graph. The 499 core seed names are routing priority only, not completeness certificates (`hepgraph/core_nodes.py`). Existing offline HLBES, paging, normalization, identity, upstream-fault and browser tests are the regression gate. Historical local/live timings in the reports are not cloud database latency measurements.

## 2. Current upstream constraints

[INSPIRE's official REST API documentation](https://github.com/inspirehep/rest-api-doc) specifies **15 requests per five seconds per IP**, HTTP 429 with at least five seconds' wait, **1,000 results per page**, and a **10,000 result window per search**. Searches support `fields` projection, but single-record reads do not; an ID search can project fields. A projected `authors` array still returns every requested element. Search hits include `created` and `updated` timestamps; the published sort options do **not** specify an `updated` cursor or a stable change feed. Field-path searches are documented generally, but a complete `created`/`updated` range query, deletion feed, or reliable incremental watermark was **not established** from the official API documentation. Do not build correctness on one without a bounded validation and INSPIRE confirmation. No supported bulk literature dump/export endpoint was established in the same documentation. Ask INSPIRE for an approved bulk acquisition or feed before full bootstrap; otherwise use rate-limited, narrow, disjoint partitions and reconcile them, checking every partition is below the result window.

[INSPIRE terms](https://help.inspirehep.net/knowledge-base/terms-of-use/) permit reuse of HEP metadata under CC0 with caveats. Downloading email addresses is prohibited. Abstracts and keywords have source-specific restrictions. This design requests neither, and stores no PDFs, full text, snippets, citations, phone numbers, or private notes. A large harvest should be coordinated with INSPIRE so it does not interfere with service. INSPIRE can alter or delete records without notice, which requires tombstones and reconciliation.

## 3. Minimum projection and provider contract

Keep a compact canonical work record with: INSPIRE literature recid; one stable internal dense integer ID; document type / correction eligibility; **true** author count; ordered byline occurrence IDs and public names/roles as needed for the guard; stable INSPIRE author recids for resolved occurrences and an unresolved marker for others; documented date/year and source precision; DOI/arXiv keys, replacement/deleted links and source recids for duplicate normalization; upstream `updated` where supplied; compact title/date/URL evidence references. Store current public author profile recid, preferred and variant names, ORCID/INSPIRE identifiers, death date and only the adviser/identity fields actually used by the guard or genealogy. Affiliation data is only needed if a verified safeguard uses it; current discovery audit found it droppable. Keep raw source payloads, if retained for audit, in private object storage with a strict public-field allowlist, never in the hot graph tables. Unresolved bylines must not reduce `author_count` and turn a big paper into a small-team edge.

Introduce an application-level `GraphProvider` contract: `resolve_author`, `get_neighbors`, `get_neighbors_batch`, `get_edge_evidence_refs`, `get_work_metadata`, `get_graph_version`, and `get_completeness`. A neighborhood response must include graph version, filter key, members, status and reason/cursor; evidence refs are stable IDs. Implement `FixtureGraphProvider`, then `LiveInspireGraphProvider` as a wrapper over existing live retrieval, then `SnapshotGraphProvider`. Pin a version for an entire search and its evidence hydration; never mix candidate and active versions. HLBES consumes `NeighborhoodOracle`, not SQL or object-store details. Batch APIs must preserve the per-author completeness proof and `min_shared` distinct-work count. Infrastructure error is an exception or `UNKNOWN`/`PARTIAL`, never an empty `COMPLETE` result.

## 4. Bounded sample and physical layouts

The **existing** 2026-09-15 saved pilot, `data/current.json`, was measured locally on 2026-09-16. It contains historical and modern selected authors, small-team papers and one 2,932-author paper. It is selected and incomplete: 1,180 works, 5,249 people, 5,996 resolved work-author links; 1,179 works have <=10 authors. The single mega-paper would create **4,296,846 undirected pairs** if expanded as a clique. The saved JSON is 2,304,802 bytes. A minimal integer-ID work projection (ID, author count/year, incidence, source IDs, DOI/arXiv keys) serialized to compact JSON was 140,093 bytes (**119 bytes/work**, 26.7 bytes/selected person, 5.08 links/work) or 35,430 bytes gzip. This projection omits profile metadata, title/byline evidence and version/checkpoint tables; it is a **lower bound**, not a deployable complete snapshot.

For <=10 papers, this sample has 3,348 distinct undirected coauthor pairs, 3,796 pair-work references, and 6,696 directed neighbor entries. A local SQLite prototype with dense integer IDs and `work(id,recid,n,year,refs)` plus indexed `inc(author,work)` used **184,320 bytes**. Adding precomputed directed `(author,neighbor,work)` small-team adjacency used **389,120 bytes total**. The 2,932-author paper contributes only 2,932 incidence rows. These sizes include SQLite pages/indexes but omit author profiles and full evidence. Thirty warmed local query runs (no network, tiny sample) had median single/batched <=10 neighborhood times of **0.053/0.055 ms** on incidence and **0.026/0.031 ms** on the hybrid adjacency. These are local algorithm comparisons, not expected Vercel latency; cold connections, network, large degrees, identity and evidence hydration will dominate. Existing live retrieved-byte measurements above are the network sample. The sample did not fetch new INSPIRE records.

Use a **hybrid** physical layout: incidence `(work_id,author_id)` for all works, immutable per-version work metadata, and deduplicated <=10 `(author_id,neighbor_id)` adjacency with separate compact supporting-work refs. Avoid a row per pair *per work* in the final design when refs can be packed or indexed separately. For >10 and all-paper modes traverse indexed incidence, aggregate distinct eligible work IDs, and apply year and `min_shared` after deduplication. A threshold beyond 10 may be tested later with real distribution and latency measurements. Dense internal IDs reduce hot index size; public INSPIRE IDs remain at the boundary. One paper cannot be split across version partitions without preserving all byline membership. Genealogy uses separate typed edges and evidence.

## 5. Full-size extrapolation and options

No verified current corpus count or large-team distribution was obtained in this phase. **Scenario only:** at the pilot's 5.08 links/work and 119-byte minimal projection, 1 million works imply about 5.1 million incidence rows, 119 MB minimal JSON (30 MB gzip if the pilot compression ratio held), 156 MB incidence SQLite and 330 MB hybrid SQLite by linear scaling. At 5 million works the same arithmetic yields 25.4 million links, 595 MB minimal JSON, 780 MB incidence SQLite and 1.65 GB hybrid SQLite. This is a lower-bound sensitivity calculation, **not** an INSPIRE size estimate: author/profile metadata, source evidence, more mega-collaborations, DB fill/indexes, immutable candidate overlap, backups and nonrepresentative selection can multiply it. Measure a stratified, approved acquisition before choosing capacity or claiming cost accuracy. Explicit adjacency for one 2,932-author paper alone would add 4.3 million pairs and is ruled out.

| Option | Query/update fit | Main tradeoff |
|---|---|---|
| Managed/serverless Postgres only (Neon, Supabase, Aurora via Vercel Marketplace) | Indexed incidence and small-team adjacency, transactional active-version pointer | Simple serving; candidate and history tables may grow; compute/connection latency |
| **Postgres + private immutable object snapshots** | Postgres hot indexes, profiles, version pointer; private object store for source evidence, manifests and rebuild artifacts | Recommended; keeps hot DB lean and gives reproducible rollback; two stores and a promotion protocol |
| Private object shards only, optional later persistent worker | Cheap immutable shards and large sequential scans | Random neighborhood reads may need many object fetches; not a good first Vercel path without a worker/cache |

[Vercel's Marketplace storage docs](https://vercel.com/docs/marketplace-storage) list Neon, Supabase and Aurora Postgres, recommend regional colocation and connection pooling. [Vercel Postgres is no longer offered for new projects](https://vercel.com/docs/postgres). [Private Vercel Blob](https://vercel.com/docs/vercel-blob/private-storage) requires authenticated reads and can hold immutable artifacts; use server-side credentials only. Alternatives such as private S3/R2 can be evaluated at provisioning time. The Vercel function queries the database with a pooled, read-only credential, reads private evidence blobs only server-side, and returns the same bounded API shape; it never serves a raw graph/snapshot file to browsers. Do not load the full graph into each function instance. Keep live INSPIRE for new identity resolution, freshness checks, evidence hydration and bounded fallback, with a **shared** upstream request limiter if instances scale out.

[Current Neon Launch pricing](https://neon.com/pricing) is $0.106/CU-hour plus $0.35/GB-month, with scale-to-zero and pooling; [Supabase Pro](https://supabase.com/pricing) starts at $25/month with 8 GB database storage included. [Vercel Blob](https://vercel.com/docs/vercel-blob/usage-and-pricing) lists $0.023/GB-month and operation/transfer charges in its displayed region; rates vary by region. A **provisional** 1-5 GB private artifact store costs about $0.02-$0.12/month for storage alone; a 1-10 GB Neon DB with 100-500 CU-hours costs about $11-$57/month for compute plus $0.35-$3.50 storage, before history, transfer and Vercel function charges. A continually warm 1 CU DB is about $77/month compute. Treat $15-$80+/month total as a planning envelope for modest traffic, not a quote. Usage, region, candidate retention, database size and live query mix need a measured pilot before account authorization. A future persistent graph worker is justified only if batched DB reads and pooled connections miss latency targets.

## 6. Exactness and completeness

Define `G(V,F)` as the graph built by the published normalization/identity policy for immutable version `V` and filters `F`, using **all** eligible records in its declared coverage through cutoff `T`. A `COMPLETE` snapshot neighborhood requires validated global or partition coverage for that author's qualifying works and any enabled genealogy, with no missing/deleted/unresolved-source ambiguity that could change its neighbors. A complete candidate is published only after every required partition and invariant passes. A snapshot may be complete *through T* and stale after T; label HLBES's `EXACT` as **“Exact shortest path in graph through T”**, with version and coverage visible. Do not imply present-day global shortestness merely from the snapshot's age. Same-node zero-hop and verified direct-edge one-hop are shortest under the selected graph definition, provided identity/evidence remain valid. For higher distances, unqualified present-day exactness needs complete, version-consistent coverage of all eligible changes after T for every neighborhood closing HLBES's lower bound, or an authoritative current complete version. The official incremental guarantee is unproven, so default to time-scoped exactness.

A new live-only author has `UNKNOWN` snapshot coverage. A live edge after T can be a verified route and may shorten a snapshot result; it invalidates any current exact claim unless all proof neighborhoods are recomputed/certified against one union view. Mixed snapshot/live traversal may show `VERIFIED` with linked evidence, but cannot raise the completed radius from a partial overlay. Failed candidate build leaves active V serving; no candidate bytes enter searches. Provider timeout, missing shard, DB error, identity conflict or inconsistent page total makes the affected neighborhood `PARTIAL`/`UNKNOWN` or the search `SEARCH_INCOMPLETE`, never an empty `COMPLETE`; `NO_PATH` requires complete exhaustion in the declared graph. Pin version and filter for the entire route/proof and hydrate all displayed edge evidence from that version or verified live refs. Clearly distinguish a route verified now from shortestness only proven through T.

## 7. V0.3 manual bootstrap, refresh, promotion and recovery

1. One deliberate maintainer action starts a **full** candidate build on temporary cloud/batch compute. Obtain INSPIRE guidance for a supported bulk mechanism first; otherwise use bounded, rate-compliant, stable partitions below the 10,000-result window. The builder checkpoints partition queries, expected/received counts, cursors, checksums and failures in private storage so an interrupted build can resume without touching production. Pagination alone is not a consistent source snapshot. Record a defensible `source_cutoff`; no silently skipped or saturated partition may receive a completeness certificate.
2. Separate acquisition, graph compilation, validation, loading and promotion. An incomplete candidate remains `CREATED`/`FETCHING`/`BUILDING`/`FAILED`; only independent completeness, identity, graph, evidence, scientific regression and index checks can mark it `READY`. Run the same gates on **every** manual refresh. Record immutable snapshot ID, schema, code commit, cutoff, source description, counts and checksums. Compare candidate neighborhoods against the retained live provider and benchmark representative end-to-end paths. Do not promote a pilot or a partial local fixture.
3. Preview `READY` candidate B in a Vercel preview deployment, pinned to B, while production serves A. Test researcher resolution, filters, direct/two-/multi-hop routes, exact versus verified labels, progressive delivery, cancellation, evidence, genealogy, exports and share links. Explicit maintainer promotion atomically changes one active-version pointer **after** private artifacts and indexes are durable. Each resumable search stores and asserts its pinned version, including evidence reads; no mixed A/B response is allowed.
4. Retain A after promoting B. Rollback reverses the pointer in one transaction without a rebuild or redownload; test this operation before cutover. A failed candidate must never alter A. Show snapshot ID, build time, cutoff, age and validation state in a maintainer-visible status. Keep at least active and previous known-good versions; no automatic deletion, expiry, staleness alarm or scheduled update compute is part of v0.3. Backups, least-privilege credentials and restore drills remain pre-cutover requirements.

The manual interface must expose `build`, `resume`, `status`, `validate`, `benchmark`, `preview`, `promote` and `rollback` without ad-hoc SQL or hand-edited pointers. The exact commands are not yet implemented; see `GRAPH_OPERATIONS.md` for current operational status. A future scheduler could call the **same** build and validation pipeline, but must not be added in v0.3. Incremental deltas, CDC, polling, scheduled reconciliation and automatic promotion are likewise deferred.

The current manifest importer and atomic saved JSON publisher are reusable ideas, **not** proof of full-corpus coverage (`hepgraph/pipeline.py`). Do not claim atomicity across DB and object storage merely because each write succeeded; verify immutable blobs first, then flip the DB pointer. Keep a single active publisher via lock/lease, with idempotent version keys.

## 8. Public-repo and implementation plan

`data/current.json` is a committed **small, explicitly partial pilot** (2.3 MB), not production data. `.gitignore` covers `data/cache`, DB files, `.env*` and generated logs, but does **not** broadly exclude a future `data/production/` or arbitrary snapshot JSON. Add explicit production artifact ignores plus a CI tracked-file size/path/secret scan before ingestion; never use Git LFS for production graph data. Keep sample fixtures tiny, synthetic or clearly partial and license-safe. Never put database URLs, blob tokens, production logs, dumps or private manifests in commits or build output. Restrict cloud roles: reader for Vercel, writer/promoter for update job, encrypted private storage, TLS, rotation and least privilege. A public clone should retrieve only code and bounded fixtures. Existing source and fixture files were not changed in this phase.

**V0.3 implementation order:** (1) add provider contract and fixture/live adapters, preserving HLBES and identity behavior; (2) build a private local **synthetic** hybrid schema and benchmark harness, including skewed authors, filters and mega-papers; (3) add a validated snapshot provider with version-pinned searches and evidence; (4) obtain INSPIRE bulk guidance and a bounded stratified sizing sample, revise build and monthly serving costs; (5) select/provision a private DB and object store with user account authorization; (6) implement resumable full manual build, independent validator, staged loader, atomic promotion and rollback; (7) shadow-read and preview on Vercel, compare paths/evidence/completeness, measure p95; (8) switch production only after the acceptance gates pass. Do **not** implement a scheduler, incremental importer or automatic reconciliation during v0.3.
